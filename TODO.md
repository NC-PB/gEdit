## Bugs and risks

### NC correctness

- [ ] **Number classes, what is left**: there is no IS-A preset; the 0.001-count option of the Fanuc feed parameters is not modelled (inverse-time and per-tooth feeds get no value at all, which is the safe answer); a real conversion of a Sinumerik `G931` travel time belongs with M10's checks ([numbers.ts](src/lib/core/machines/numbers.ts), [syntax-fanuc §3.2](docs/planning/syntax/syntax-fanuc.md#32-numbers))
- [ ] **Tokenizer gaps, what is left**: an unclosed string or `[` runs to the line end (for `[` the comment mask disagrees); a Klartext `PLANE POINTS P1X+0` word (a digit inside the address, then a sign) is one unknown token; a Sinumerik jump written without a blank, `GOTOF:20`, still tokenizes as a label (Renumber and Remove Block Numbers follow it since the second M9 review round, which reads the main-block scan alone; hover and other readers see a label named `GOTOF`) ([tokenizer.ts](src/lib/core/nc/tokenizer.ts))
- [ ] **Tool-word variants, small gaps**: under the Okuma three-digit reading a six-digit word is not a tool change, and station names from the seven-digit form (`02`) and from `T2000` (`2`) are not normalised, so a file mixing both would split a tool in two (no real program does); under the Fanuc last-digit reading a short word `T1` is the station alone ([r6Variants.test.ts](src/lib/data/profiles/r6Variants.test.ts), [syntax-okuma §5.1](docs/planning/syntax/syntax-okuma.md#51-t-word))
- [ ] **The contradiction guard has no certain evidence for a Fanuc mill program read as Okuma** — their syntax is shared; the guard refuses only on `#` variables, a Fanuc lathe `P`/`Q` cycle, `G15 H`/`G16 H`, `G56 H` without `G43`/`G44`, or `SB=`. The gap is written down in [dialects.md](docs/user/dialects.md#which-dialect-a-file-gets) and waits for a manual of the Okuma machining-centre control (low priority) ([contradiction.ts](src/lib/core/profiles/contradiction.ts))
- [ ] **Okuma after M8**: a thread code on a `$` line does not protect the F above it (documented); one map item per line (`NEND M02` is listed as the end, not as the label `NEND`); renumbering protects `$` lines only through the editable `skipStartingWith` list, never through `continuationStart` (with `$` taken out, `N30 $ H1.8 …` cuts the lead line off its block); the program map's G-code macro rule stops at `G171` (the calls run to `G176`); `CALL`/`O` names stop at 4 characters (16 with an option) — a lead could be scaled; not taken in M9 ([syntax-okuma §11.7](docs/planning/syntax/syntax-okuma.md#117-after-m8-g10-review-what-the-okuma-profile-still-does-not-do), [renumber.ts:795](src/lib/core/transforms/renumber.ts#L795))
- [ ] **Code-database gaps, what is left**: a Klartext cycle the database still lacks falls to the generic `CYCL DEF` (a `CYCL CALL` after it reads as "nothing defined", fail-safe; 202, 208 and 262 arrived with the M10 prelude); Okuma `G132`/`G133`, `G119`, `G313`, `G93`, `M85`, and `G56 H` and `M54` in the machining-centre programs (R9: the manuals at hand are lathe manuals); Fanuc `G61.1` (a private program uses it, no manual here), `G41.2`–`G42.6`, `G68.1`, `G92.1`, `G29`, `G30.1`, `G05.4`, `G06.2`, `G43.1`; the Sinumerik milling cycles (`CYCLE61`, `POCKET3` …), `CUT3DCC`, `COMPSURF`, `G601`–`G603`, `G643`/`G644`, `CTOL=`/`OTOL=`/`FP=` (their feed parameters need a Scale Feed review), `WAITM`/`WAITE`/`SETM`/`CLEARM` (`G290`/`G291` arrived with M10; their labels, and those of Fanuc `G15`/`G16`, need a G10 look), `CYCLE82` lists the 9 arguments of the 2009 cycle manual (the M10 prelude added the three mode arguments; anything after them refuses address arithmetic) and `CYCLE93`/`CYCLE97` have none ([codes](src/lib/data/codes), [proposal R3](docs/planning/source-review-2026-09.md#r3-5-axis-and-high-speed-codes-and-words-that-are-data))
- [ ] **M10 data gaps** — the Fanuc lathe database has no `G81` (live-tool drilling) and no `G241`/`G195` (their blocks are "unknown code" to the checks, the extents and the arithmetic); Okuma `G20`/`G21` (home position return) carry no machine-position flag; a database arc flag would replace the geometry table of `extents.py` (the pole flag is done); the standard Sinumerik milling cycles (`CYCLE61`, `POCKET4`, `SLOT1`) have no entries with position roles, so address arithmetic refuses a call with a number among its arguments and lists it; a Klartext cycle the database still lacks (`CYCL DEF 251` and others) does not replace the earlier definition in the modal state, so address arithmetic works around it and refuses; Klartext and Sinumerik cycle depths (`Q201`, `DPR`) have no "relative to the tool-axis parameter" role, so the extents count them "not resolved"; subprogram calls are not followed by the extents; after a lathe `G90`/`G92`/`G94` box cycle the extents take the written end point as the position; Okuma arcs by radius `L` are not computed ([extents.py](src-tauri/resources/scripts/extents.py), [address_arithmetic.py](src-tauri/resources/scripts/address_arithmetic.py))
- [ ] **Remove Block Numbers and a `GOTOB :20` jump** — with "keep numbers that are pointed at" off, the run writes no per-line row for such a jump, although the question before the run counts it; no M10 work package owns the transform, so it goes to the fix batch after M10 ([removeBlockNumbers.ts](src/lib/core/transforms/removeBlockNumbers.ts); P2 §6 M10, "What P10 decided")
- [ ] **Klartext polar moves are not positioning blocks under `M89`** — `LP PR… PA…` and `CP` carry no axis word, so a modal cycle call does not run on them in the modal state (the opposite gap to the one the review closed on `CC`/`BLK FORM`). The extents (M10) work them out from the pole `CC`; the modal state still does not count them ([_nc_modal.py](src-tauri/resources/scripts/_nc_modal.py))
- [ ] **Convert Case changes a Fanuc program name's letters** — `<mac_f1>` becomes `<MAC_F1>`, and names are probably case-sensitive on the control (`o123` is not a program number), so a call to the lower-case name would break; `O1234` → `o1234` has the same issue. A `programMarker` that matches `syntax.programNames` should stay unchanged, or be reported ([convertCase.ts](src/lib/core/transforms/convertCase.ts))
- [ ] **The Fanuc lathe database has no `G65`** — `l08-named-programs.nc`'s `M98 <NAME>` call works, but a `G65 <NAME>` macro call on the lathe has no entry (content task) ([fanuc-lathe.json](src/lib/data/codes/fanuc-lathe.json))
- [ ] **Small tokenizer/editing niceties left by the decision batch**: `src/lib/monaco/languages.ts`'s Klartext `wordPattern` still splits a number at the decimal point only, so double-clicking `241,781` selects `241` or `781`, not the whole number; `_nc_modal.py`'s `ModalInterpreter._apply_tool` has the same fallback-to-whole-match pattern that was fixed in `outline.ts`/`tool_list.py`, and no speed-vs-tool-change concept for Klartext's bare `TOOL CALL S…` forms; `numberClassOf` takes the codes in force since M9, so a caller passes Fanuc `G63`; the TypeScript callers of Phase 3 must do the same; `iso.ts`'s own standalone-before-skip Monarch rule may have the same "column 0" trap that was found and fixed in Klartext's (a Fanuc program that writes a block skip directly in front of the number, e.g. `/N120 G0 X0.`, was not checked against the fix — dec-klartext flagged it, not settled)
- [ ] **Script texts, what is left**: an `F` that belongs to a function — Klartext `M128 F`, `M140 … F`, a `PLANE … F`, cycle 19's `F` — is read as the path feed (a tool-list feed range of `125-1000`); the tool list drops values before an unnamed tool change and shows no `SB=` speeds (`S1=` is the main spindle's speed since M10); Scale Feed's `onlyAbove`/`onlyBelow` on a feed with no value in the limit unit is an open WP9.5a item ([tool_list.py](src-tauri/resources/scripts/tool_list.py))

- [ ] **Deferred from M12.5 (the two reviews of real programs, 2026-10-08)** — each with its reason ([the triage](docs/planning/phase-2-implementation.md#m125-real-programs-second-pass)): Sinumerik GUD variables stay `unknown` (their declarations live in GUD files gEdit does not read); builder two-letter axes (`AA<n>`, `BB<n>`, a lone `QQ0` read as a call) and a builder `G` group wait for R6's extra axis letters (§11 #26); `_N<n>` before a subprogram call (meaning unclear); Okuma blank-drawing words `WORK`, `PS`, `LC` (no manual at hand; `DEF`, `DRAW`, `CLEAR` are read); a Siemens job list (`SELECT <file> CH=<n>`) as a source for "this file is channel n" (a code feature, one shape seen); on a twin-turret Okuma machine, "Turret B not found" for a one-turret program with a single `G13` might better be information than a problem (no two-turret program to check the wording against); the Siemens turning profile's exclusion of `Y` words can still read a header-less mill-turn program as a lathe (it is now flagged as uncertain, but not told apart); and the short programs that carry no marker which tells Fanuc from Okuma (for example a mill subprogram of a few lines) are called uncertain, the honest answer under the rule — more Fanuc-only markers (`M98 P`, `M99`, `#` variables, `G10 L`) would each need a count and a manual check for Okuma first.
- [ ] **Highlighting differs from the tokens on the M12.5 `syntax` fields** (`src/lib/core/grammar/{iso,klartext,okuma,sinumerik}.ts`): the Monaco grammar has no rule for `freeText` (a Klartext cycle or program name is coloured word by word, the tokens say one `text`), `colonWords` (`VCONST:ON`, `HSC-MODE:1`), `callTargets` (Okuma `CALL OABCD` colours the name as a plain word, the tokens say `programMarker`), `labelAfter` (a Sinumerik `GOTOF SKIPSIM` target is not coloured as a label), `declareAfter` (a `DEF` name is not coloured as a variable), `plainTextRun` (a run of plain words such as `M797 SPINDLE ONE DONE` is coloured word by word, the tokens say one `unknown`) and a keyword shaped like a sequence name (`NOEX`: the grammar's sequence-number rule claims the leading `N`, the tokens read the keyword). `tapeMarker: false` is mirrored (integration I-RP). - [ ] **Scale Speed ignores a Klartext `VC:` value** (`FUNCTION TURNDATA SPIN VCONST:ON VC:120 SMAX3000`): M12.5 reads `VC:120` as a word with address `VC`, but no code-database entry marks it a cutting speed, so Scale Speed leaves it. If the owner wants it scaled, mark `VC` as a cutting-speed address in `data/codes/heidenhain.json` and add a golden to the scale-speed fixtures.
- [ ] **The comment mask is unchanged by M12.5** (`mask.ts`, `mask_comments`): `text` tokens and the new markers are not masked, so the regex readers (outline, tool call, detection) still see Klartext cycle and program names and free text as before. A word-looking name inside such text (a cycle name that reads like a tool word) can still reach those readers; no real program has shown it, so nothing was changed.

### Data safety

- [ ] **Two tabs can own one file** (a symlink, `..`, or a mapped drive next to its UNC path) — the later save silently overwrites the earlier one ([documents.ts:30](src/lib/stores/documents.ts#L30-L46))
- [ ] **Recovery gaps**: failing snapshots show one message and no lasting sign; a restore onto a path another tab owns lands in an untitled tab; a partial restore offers the restored snapshots again — false confidence ([recovery.ts](src/lib/contrib/recovery.ts), [fileOps.ts:1015](src/lib/app/fileOps.ts#L1015-L1019))
- [ ] **A same-size rewrite within 2 s on FAT32 or exFAT goes unseen** — a save can overwrite another tool's change on a USB stick ([fileOps.ts:158](src/lib/app/fileOps.ts#L158-L162))
- [ ] **A file with one stray CR among CRLF endings is not saved byte-exact** (one private Sinumerik program; the documented mixed line-ending behaviour turns the CR into a line break) — G11's round-trip check reports it (`roundTrip`, one of 17), and `knownGaps.roundTrip` is the way to accept it; say so where the guide promises byte-exact saves, or keep a lone CR as it is ([codec.ts](src/lib/core/text/codec.ts))
